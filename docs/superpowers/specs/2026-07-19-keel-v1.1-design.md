# Keel v1.1 — JavaScript, Python, and Binary Distribution Design

**Date:** 2026-07-19  
**Status:** Approved design  
**Target version:** 1.1.0

## 1. Goal

Extend Keel with deterministic JavaScript/JSX and Python indexing, then make
prebuilt binaries installable through a verified curl installer and Homebrew.

The release must preserve Keel's core constraints:

- Local-first and deterministic.
- No LLMs, embeddings, or semantic search.
- Language logic stays behind `LanguagePlugin`.
- Existing Rust, TypeScript/TSX, and Go behavior remains compatible.
- Release artifacts are reproducible enough to verify by SHA-256.

## 2. JavaScript / JSX plugin

Add `tree-sitter-javascript` and a built-in `JavaScriptPlugin`.

### Extensions

- JavaScript grammar: `.js`, `.mjs`, `.cjs`
- JSX grammar: `.jsx`

Use separate internal registrations when grammar selection differs, following
the existing TypeScript/TSX pattern.

### Extracted symbols

- Function declarations and generator functions.
- Class declarations.
- Class methods.
- Variable-bound arrow functions and function expressions.
- Exported declarations use the declaration's actual identifier.

`module_path` derives from the source file path with its extension stripped.

### Extracted references

- Direct function calls.
- Property/method calls.
- Constructor calls (`new`).
- Containers use the enclosing function/class/method, or the file path for
  top-level references.

### Imports

- ESM default, namespace, and named imports from string module sources.
- Aliases from `import { original as alias }`.
- Side-effect imports.
- CommonJS `require("module")` assigned to a variable.

JavaScript has no direct trait implementation syntax, so
`extract_impls` remains empty.

## 3. Python plugin

Add `tree-sitter-python` and a built-in `PythonPlugin`.

### Extensions

- `.py`
- `.pyi`

### Extracted symbols

- Module-level and nested functions.
- Async functions.
- Classes.
- Methods.
- Module constants where the binding is syntactically constant-like.

`module_path` derives from the source file path without an extension, converting
path separators to dots for Python package-style identity.

### Extracted references

- Function calls.
- Attribute/method calls.
- Constructor calls (represented as calls).
- Containers use the enclosing class/function hierarchy or file path.

### Imports

- `import package` and aliased forms.
- `from package import name` and aliases.
- Relative imports preserve leading-dot semantics deterministically.

Python protocols and inheritance are not equivalent to explicit Rust trait
implementation. For v1.1, class bases may be recorded as implementation-like
relationships only when extraction is unambiguous; otherwise `extract_impls`
remains conservative.

## 4. Registry and indexing integration

Register both plugins in `Registry::with_defaults()`. The current extension-aware
crawler and watcher automatically pick them up through `Registry::extensions()`.

Add:

- Focused parser/extractor unit tests for each language.
- Integration fixtures proving `.js`, `.jsx`, `.py`, and `.pyi` files are
  indexed by one mixed-repository pass.
- Regression coverage proving existing languages remain indexed.

## 5. Release artifacts

GitHub Actions publishes release assets when a `v*` tag is pushed.

### Targets

| Platform | Rust target |
|----------|-------------|
| macOS Apple Silicon | `aarch64-apple-darwin` |
| macOS Intel | `x86_64-apple-darwin` |
| Linux x86_64 | `x86_64-unknown-linux-gnu` |
| Linux ARM64 | `aarch64-unknown-linux-gnu` |

Each artifact is:

```text
keel-<version>-<target>.tar.gz
```

The archive contains:

- `keel`
- `README.md`
- `CHANGELOG.md`

The workflow also publishes `SHA256SUMS`.

The release workflow runs the full test suite and clippy before packaging.
Cross-compiled Linux ARM64 binaries use a maintained cross-compilation action or
toolchain rather than silently publishing host-architecture binaries.

## 6. Curl installer

Add a POSIX shell `install.sh` that:

1. Detects `Darwin` or `Linux`.
2. Detects `x86_64` or `arm64`/`aarch64`.
3. Resolves the requested version (`KEEL_VERSION`, default `latest`).
4. Downloads the matching archive and `SHA256SUMS` from GitHub Releases.
5. Verifies SHA-256 before extraction.
6. Installs `keel` into `${KEEL_INSTALL_DIR:-$HOME/.local/bin}`.
7. Prints PATH guidance when the install directory is not on PATH.

It fails closed for unsupported platforms, missing checksums, mismatched hashes,
and network errors.

The documented command is:

```bash
curl -fsSL https://raw.githubusercontent.com/ashokdudhade/keel/main/install.sh | sh
```

## 7. Homebrew

Add `Formula/keel.rb`, consuming the same tagged release archives and SHA-256
values.

Initial installation:

```bash
brew install --formula \
  https://raw.githubusercontent.com/ashokdudhade/keel/main/Formula/keel.rb
```

The formula supports macOS ARM64 and Intel. Linuxbrew may use the Linux archives
when Homebrew's platform blocks can express the required target selection.

The formula test runs:

```bash
keel --help
```

Formula hashes must correspond to an actual GitHub Release. The release process
therefore generates or updates the formula after assets are available; it must
not commit placeholder checksums.

## 8. Versioning and documentation

- Bump Cargo package version to `1.1.0`.
- Update `CHANGELOG.md`.
- Update root and crate READMEs with JavaScript/Python support and install paths.
- Document that the crates.io name `keel` is already occupied; supported public
  installation is GitHub binaries/Homebrew unless a distinct crate package name
  is chosen later.

## 9. Testing and acceptance

The release is accepted when:

- All existing and new Rust tests pass.
- Clippy with `-D warnings` passes.
- JavaScript, JSX, Python, and Python stub integration fixtures produce expected
  definitions, references, and imports.
- A mixed Rust/TypeScript/JavaScript/Python/Go repository indexes in one pass.
- `install.sh` passes shell syntax checks and installer tests using a local mock
  release server or fixture archives.
- Every published archive runs `keel --help` on its target platform.
- The Homebrew formula installs from real release assets and its test passes.

## 10. Deferred

- Node package resolution using `package.json`, workspaces, and `node_modules`.
- Python environment resolution using `pyproject.toml`, namespace packages, and
  installed distributions.
- JavaScript dynamic imports and non-literal `require`.
- Python runtime monkey-patching and dynamic imports.
- Submission to `homebrew-core`; the in-repository formula is the v1.1 scope.
